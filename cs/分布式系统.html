分布式系统

分布式系统的根本矛盾：多个节点各自有独立状态，但你希望它们像一个整体一样运行。所有分布式算法本质上都在处理 部分故障 和 不确定性。

核心概念

为什么需要分布式系统

动机说明
扩展性 (Scalability)单机瓶颈 → 多机分担负载
容错 (Fault Tolerance)单机故障不影响整体服务
低延迟 (Latency)数据靠近用户（地理分布）
隔离 (Isolation)不同服务独立部署和演进

时间与顺序

分布式系统中没有全局时钟。替代方案：

  • 物理时钟：NTP 同步，精度 ms 级（Spanner 用 GPS + 原子钟达到 μs 级 TrueTime）
  • 逻辑时钟 (Lamport Clock)：C(a)<C(b) 不蕴含 a happens-before b
  • 向量时钟：可检测并发事件（Va​<Vb​⟺a→b）

CAP 定理

一个分布式系统最多同时满足三者之二：

选择含义典型系统
CP (一致性 + 分区容错)分区时牺牲可用性ZooKeeper, etcd, HBase
AP (可用性 + 分区容错)分区时牺牲强一致性Cassandra, DynamoDB, CouchDB
CA无分区假设（单机）传统关系型数据库

CAP 不是”三选二”的设计选择——分区必然发生，实际选择是在 CP 和 AP 之间。无分区时，C 和 A 可以兼得。

PACELC 扩展

  • 有分区 (P) 时：选 A 还是 C？
  • 无分区 (E) 时：选 L（延迟）还是 C（一致性）？

一致性模型

从强到弱排列：

模型保证典型系统
线性一致性 (Linearizability)操作表现得像瞬间原子执行，尊重全局实时顺序etcd, ZooKeeper
顺序一致性所有节点看到相同的操作顺序（但不保证实时顺序）Zookeeper (默认)
因果一致性有因果关系的操作按序可见COPS, MongoDB (causally consistent sessions)
最终一致性若无新写入，最终所有副本收敛DNS, Cassandra (默认), DynamoDB (默认)
读己之写客户端总能读到自己的写入许多系统的 session 保证

强一致性的代价

线性一致性需要多数派确认或 leader 协调，延迟不可压缩到光速以下。Paxos/Raft 的一个写操作至少需要 1 个 RTT。

共识算法

Paxos

Leslie Lamport (1989)。角色：Proposer, Acceptor, Learner。

  • Basic Paxos：两阶段（Prepare/Promise → Propose/Accept），达成单个值的共识
  • Multi-Paxos：选出一个稳定 Leader 后，跳过 Prepare 阶段 → 每个实例只需一个 RTT

Raft

Ongaro (2014)，以可理解性为目标。三个子问题：

  1. Leader 选举：随机超时，获得多数票者当选
  2. 日志复制：Leader 将日志同步到 Follower，多数确认后 commit
  3. 安全性：Leader 的日志必须包含所有已 commit 的条目
特性PaxosRaft
可理解性困难清晰
成员变更复杂联合共识 (Joint Consensus)
实现工程细节多规范性强

实际考量

共识算法本身只保证日志一致。上层需要状态机复制 (State Machine Replication) 才能实现容错服务。

复制策略

策略机制优点缺点
主从复制所有写→主，读→从简单写瓶颈，failover 可能丢数据
多主复制多个节点可写写扩展冲突解决复杂
Quorum 读写W+R>N可调一致性与延迟需谨慎配置
链式复制写→head→tail，读→tail强一致 + 高读吞吐写延迟长

分片 (Sharding)

将数据按某种键分区到不同节点。

分片策略示例挑战
范围分片key ∈ [A–M) → shard 1热点（如时间序列 key）
哈希分片hash(key) % N均匀但范围查询困难
一致性哈希ring 上分配虚拟节点加减节点只迁移少量数据
目录分片查表定位灵活但引入额外查找

MapReduce

Google (2004) 提出的批处理模型：

  1. Map：(k1​,v1​)→list(k2​,v2​)
  2. Shuffle：按 k2​ 分组
  3. Reduce：(k2​,list(v2​))→list(v3​)

核心思想：将数据移动（shuffle）限制在 Map 和 Reduce 之间，Map 阶段在数据所在节点执行。

分布式事务

两阶段提交 (2PC)

  1. Prepare：协调者询问所有参与者能否提交
  2. Commit/Abort：所有人都回答 Yes 则提交，否则中止

致命缺陷：协调者崩溃后，参与者阻塞等待（阻塞问题）。

三阶段提交 (3PC)

增加 PreCommit 阶段和超时机制，减少阻塞但增加了消息轮数和复杂度。

Percolator / TiDB 模型

基于分布式锁 + MVCC + 异步清理。避开全局锁管理器，适合大规模稀疏事务。

常见丢分点

  1. CAP 不是”只能同时满足两个”——分区发生时你必须选，分区愈合后可以 C+A 兼得。
  2. Paxos/Raft 保证的是共识安全性和活性，不保证低延迟。
  3. 最终一致性 ≠ 没有顺序保证。CRDT、向量时钟等机制可以在最终一致性下提供合理语义。
  4. 2PC 的阻塞问题是可用性杀手——Google Spanner 通过 Paxos 冗余协调者 + TrueTime 来绕过。
