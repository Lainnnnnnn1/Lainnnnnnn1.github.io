数据库 Database

人话讲解

数据库不只是「存数据的地方」。它解决的是一个看似简单实则极难的问题：怎么保证 100 个人同时读写同一份数据，结果还是对的？ 从银行转账（绝对不能少一分钱）到微博热搜（无所谓偶尔数据不一致）——不同场景需要不同的数据库。

「There are only two hard things in Computer Science: cache invalidation and naming things.」— Phil Karlton （数据库又是 cache 又是 name，双重痛苦）

JOIN 类型对比

JOIN结果行NULL 出现适用
INNER两表都匹配的行无只要有关联的数据
LEFTA 全部 + B 匹配B 侧可能 NULL以 A 为主（A 是「1」侧）
RIGHTB 全部 + A 匹配A 侧可能 NULL以 B 为主
FULL OUTER两边全部两侧都可能找「两边都对不上」的数据
CROSS|A|×|B| 行无组合枚举

例题：统计每门课的选课人数，没人选的课也要显示（人数为 0）→ 必须 LEFT JOIN 以 courses 为主表，COUNT 数 enrollments 的 id 而不是 *（否则 NULL 行被数成 1）。

事务与 ACID

事务 = 一组要么全做、要么全不做的操作。

ACID 四要素

属性含义违反的后果
Atomicity 原子性要么全成功，要么全回滚转出扣了钱，转入没加上
Consistency 一致性事务前后数据都满足约束余额变负数
Isolation 隔离性并发事务互相不影响脏读、不可重复读、幻读
Durability 持久性提交后数据不丢失银行说转账成功，断电后钱没了

隔离级别 Isolation Levels

┌──────────────┬────────┬──────────┬────────┐
│ 隔离级别       │ 脏读    │ 不可重复读 │ 幻读    │
├──────────────┼────────┼──────────┼────────┤
│ Read Uncommitted│ ✅    │ ✅       │ ✅     │
│ Read Committed  │ ❌    │ ✅       │ ✅     │
│ Repeatable Read │ ❌    │ ❌       │ ✅     │
│ Serializable    │ ❌    │ ❌       │ ❌     │
└──────────────┴────────┴──────────┴────────┘
✅ = 可能发生，❌ = 阻止

三个问题：脏读 = 读到别人未提交的数据；不可重复读 = 同一次事务里两次读同一行结果不同（别人改了）；幻读 = 同一次事务里两次范围查询行数不同（别人插了）。

锁与隔离的实现

锁作用
共享锁 S读读可共存，读写互斥
排他锁 X写写互斥、读写互斥

两阶段锁 2PL：事务先加完所有锁才能解锁——保证冲突可串行化。MVCC（多版本并发控制）：读操作读历史快照，不阻塞写——MySQL InnoDB 的默认方案。

索引 Index

没有索引 = 全表扫描 O(n)，有索引 = O(log n) 甚至 O(1)。

B+ Tree — 数据库索引的标配

                [30 | 70]
               /    |    \
      [10|20]     [40|50|60]    [80|90]
      /  |  \     / |  |  \    /  |  \
    叶子节点（链表连接，存实际数据）

为什么是 B+ Tree？

  1. 矮胖 — 高度低（3-4 层就能索引百万行），减少磁盘 I/O
  2. 叶子链表 — 范围查询 O(log n + k)，顺序扫描快
  3. 自平衡 — 插入删除自动分裂/合并

扇出计算例题：页大小 16KB，键 8 字节 + 指针 8 字节 → 每节点 ⌊16×1024/16⌋ = 1024 个键，扇出约 1025 → 树高 h = 磁盘 I/O 次数：3 层 ≈ 100 万条，4 层 ≈ 10 亿条。

聚簇 vs 非聚簇索引

聚簇索引 Clustered非聚簇索引 Secondary
叶子节点存什么整行数据主键值
每表数量只能有一个（InnoDB 主键）可以有多个
回表不需要需要（按主键再查一次）
覆盖索引—查询列都在索引里 → 免回表

例题：SELECT name FROM students WHERE gpa > 3.0，若建了 (gpa, name) 复合索引 → 索引覆盖，不用回表，快。

规范化 Normalization

范式规则
1NF每列原子性（不能存数组）
2NF非主属性完全函数依赖主键（消除部分依赖）
3NF非主属性不传递依赖主键（消除传递依赖）
BCNF每个决定因素都是候选键

范式判断例题

例题 1：关系 R(A, B, C, D)，函数依赖 A → B, B → C, C → D。候选键是 A。

A → B → C → D 是传递依赖（D 经过 B、C 传递依赖 A）
→ 属于 2NF，不满足 3NF
分解成 3NF：R₁(A, B), R₂(B, C), R₃(C, D) —— 每条函数依赖一张表

解题思路：① 找候选键；② 检查非主属性是否完全依赖候选键（否则违反 2NF）；③ 检查有无传递依赖（否则违反 3NF）；④ BCNF：所有函数依赖的左侧都必须含候选键。

例题 2：选课表（student_id, course_id, dept），主键 (student_id, course_id)，但 dept 只依赖 course_id → 部分依赖 → 违反 2NF。拆成：选课(student_id, course_id) + 课程(course_id, dept)。

CAP 定理

一个分布式系统最多同时满足其中两个：

一致性 Consistency：所有节点看到相同数据
可用性 Availability：每个请求都有响应
分区容错 Partition Tolerance：网络断开时系统继续工作

CP: MongoDB, HBase (一致性+分区容错，牺牲可用性)
AP: Cassandra, DynamoDB (可用性+分区容错，牺牲一致性)
CA: 传统 RDBMS 单机（一致+可用，但不分区容错）

查询优化

二级结论速查

  1. SQL 执行顺序：FROM → WHERE → GROUP BY → HAVING → SELECT → ORDER BY → LIMIT
  2. WHERE 过滤行，HAVING 过滤组；聚合结果只能进 HAVING
  3. 函数包住索引列 = 索引失效（YEAR(order_date)）
  4. 复合索引最左前缀：从最左列开始连续匹配才有效
  5. 隔离级别越高越安全越慢：MySQL 默认 Repeatable Read，PG 默认 Read Committed
  6. B+ 树矮胖 + 叶子链表 = 少 I/O + 范围查询快；树高 = I/O 次数
  7. 范式是「拆表」的艺术：1NF 拆列、2NF 拆部分依赖、3NF 拆传递依赖
  8. JOIN 选型：要「1 侧全保留」用 LEFT/RIGHT JOIN，找孤数据用 FULL OUTER JOIN

常见坑

  1. SELECT * 在生产环境 — 表加列可能导致意外的带宽/内存暴增
  2. N+1 查询 — 循环里逐条查，改成 JOIN 或批量查询
  3. 索引不是越多越好 — 每个索引都要维护（写变慢 + 占空间）
  4. 事务不提交/不回滚 — 一直占着锁，把整个表锁死
  5. 连接池耗尽 — 数据库连接没归还，服务器 502
  6. SQL 注入 — 永远用参数化查询，绝不拼接字符串！
