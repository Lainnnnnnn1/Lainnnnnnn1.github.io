实盘教训

渡鸦从零到实盘跑起来的全过程。每一个坑都是真金白银踩出来的。

资金规模与心态

14.72USDT起步。这是伙食费级别的测试资金，不是"投资"。对亏损极度敏感——亏1.47 是 10%，一顿饭钱。所以所有风险描述用具体金额，不用百分比。

第一笔交易：76 WIF @ 0.1534，卖出@0.1546，净赚 $0.06。钱少得可笑，但全链路验证了：API 连接 → 信号生成 → 安检 → 下单 → 成交。

教训： 小资金的第一价值不是赚钱，是跑通全链路 + 建立对亏损的敬畏。第一笔 $0.06 的利润证明了系统能闭环，这比利润本身值钱得多。

真实案例一：意外真下单（最贵的一课）

7 月 17 号凌晨：测试 SOL 买入时代码真执行了，真金白银被意外买入。

根因： 测试代码复用了生产的下单函数，没走测试端点。

修正：

  1. 任何涉及 API Key 的测试命令，必须先加 try/except 或 limit order 远低于市价
  2. 绝不能用 market order 做测试
  3. runtest.py 中改用 /api/v3/order/test 端点——币安提供的测试下单，不真成交。运维全链路运检必须走这个，不能走真下单

真实案例二：假突破与缩量阴跌

布林带收窄后向上突破，五道过滤里 RSI、布林、SMA50 全部满足，但 rvol = 0.4（缩量）——渡鸦没买（rvol ≥ 0.7 的条件拦住了）。随后价格 20 分钟内回落 3%，假突破确认。

对照案例： 另一次同样是布林突破，但 rvol = 2.1 放量突破，买入后吃到 4% 行情。

教训： 量价配合是过滤假信号最便宜的一层。放量突破可能是真的，缩量突破大概率是骗线——指标会说谎，成交量不常说谎。

真实案例三：踏空——策略失效的另一种形式

BTC 单边上涨 10%，RSI 连续数天 > 70，渡鸦一个买入信号都没有。账户空仓，看着行情走。

教训： 踏空不是 bug，是均值回归策略的固有属性。趋势市里它就该空仓。判断策略是否失效要看它的适用环境，而不是看它没赚钱——震荡市里它还赚不赚，才是它该回答的问题。

真实案例四：浮盈变浮亏

一笔交易涨到 +6% 没触发任何卖出条件（分层止盈第一层是 +5% 或 RSI > 60——当时 RSI 还在 55 以下，策略按规则持有），随后 40 分钟内跌回 -3%。如果没有分层止盈的 +5% 第一层，这笔会从 +6% 变 -5% 止损出局。

教训： 分层止盈牺牲了 +6% 到 +8% 的部分上行，换来的是「浮盈锁一半」。在 15 分钟级别，+5% 的利润 40 分钟内可以蒸发——落袋的一半才是真利润。

真实案例五：小币种滑点

某小市值币种，盘口买一卖一价差 0.8%。市价买入后立即显示浮亏 1.2%（滑点 + 手续费 0.2%）。还没开始赚，就已经亏了 1%+。

教训： 流动性是隐藏成本。选币先看价差（spread）和盘口深度，再看波动率——波动大但没人接盘的币是陷阱。渡鸦只做前 20 流动性最好的币种，就是这个原因。

技术栈选择：为什么放弃 ccxt

ccxt 在 macOS 上 load_markets() 会挂——dapi.binance.com SSL EOF + Rate Limit 耗尽。调了一个通宵，最后结论：纯 REST API 更可靠。

纯 Python requests + hmac 签名直调币安 REST API。没有中间层，出问题一眼看到。

签名机制要点： 参数必须按 key 排序后拼成 query string，再 HMAC-SHA256 签名——顺序错了签名就错。timestamp 用毫秒。这是所有币安系 API 的公共知识，值得背下来。

币安 API 代码示例：下单与余额

限价单（生产用，不用市价单）

三个要点：

  1. test 参数——运检测试永远走 /order/test
  2. newClientOrderId——自定义订单 ID，网络重试时用它查重，防止重复下单
  3. LIMIT + GTC——限价单不追价，滑点可控；市价单只在明确要立即成交时用

余额校验（每轮循环必查）

渡鸦主循环中 fetch_balance() 返回值异常——显示金额 0或2 而非实际余额，导致买入信号全部被安检拦截。独立 Python 脚本中相同 API 调用正常。

根因：可能是 load_markets() 的 side effect 或 rate limit 耗尽。不纠结原因——改用纯 REST 直接调 /api/v3/account，不再经过 ccxt。每轮交易前校验余额，余额对不上就跳过本轮——宁可错过信号，不可带着错误余额下单。

币安 API 域名

在中国大陆：

  • api.binance.com → 被墙
  • api1.binance.com → 偶尔被墙
  • api-gcp.binance.com → 谷歌云节点，直连可用
  • data-api.binance.vision → 直连可用

渡鸦固定用 api-gcp。不经过代理——代理会引入延迟和不确定性。

IP 白名单

币安 API Key 的 IP 白名单只支持精确 IP，不支持 CIDR 格式。用户的公网 IP 是 213.218.254.x 段，运营商 DHCP 偶尔换 IP。IP 变了→API Key 失效→渡鸦停摆。

解决方案：定时检查 API 连通性。断了就通知，手动更新白名单。没有自动化这个——安全第一。

时间同步

币安要求请求时间戳与服务器时间差不超过 recvWindow（默认 5000ms）。本地时钟偏了 → 请求被拒。

每次启动渡鸦先 sync_time，所有请求的 timestamp 都加上 TIME_OFFSET。

错误处理模式

币安 REST 的错误码比报错文本有用，先查码再查文：

错误码含义处理
-1021时间戳偏差超过 recvWindow重新 sync_time，重发
-2014 / -2015API Key 无效 / 签名错误检查 Key 和签名逻辑，人工介入
-1003请求过于频繁（限频）指数退避重试，降低频率
429限频（HTTP 层）退避 + 熔断
-2019余额不足跳过信号，记日志
-1100参数非法检查参数类型（价格/数量必须字符串）

指数退避重试

重试的边界： 查询类请求随便重试；下单请求重试必须带 newClientOrderId 查重——否则网络抖动时同一笔单可能下两次。这是实盘事故最常见的来源之一。

API 熔断： 连续 5 次请求失败 → 停止所有交易动作，只保留余额监控和告警，等人工确认。宁可错过行情，不可带着半坏的管道乱下单。

$15 账户的仓位困境

$14 的账户只能持 1 个仓位。卖了才能买下一个——机会成本巨大。用户对”钱被锁在单一仓位错失机会”极度不满。

这个问题的根因不是策略，是资金量。资金量 < 50时，分散持仓没有意义——单笔最小10（币安现货最低 10 USDT 等值），手续费占比太高。小资金的核心是验证系统，不是赚钱。

熔断机制：为什么需要

  • 单笔最大亏损：$1.18（8% 止损）
  • 连亏 5 笔触发熔断：24 小时停止交易
  • 最差情况：$5.90 亏损 + 1 天冷静期

这不是”不信任策略”——策略会失效，市场会变，黑天鹅会发生。熔断是最后一道防线。

熔断的另一层价值： 连亏 5 笔说明策略与当前市场环境不匹配（比如震荡策略遇到趋势市）。24 小时冷静期不是惩罚，是给策略一个「重新评估环境」的机会。

日志与监控设计

实盘系统的另一半是日志——没有日志，出事只能猜。

交易日志（每次决策必记）

字段示例用途
时间戳2026-07-17 03:12:45复盘时间线
币种/周期SOL / 15m定位
信号值RSI=32, rvol=1.3信号可复现
决策BUY 0.5 SOL @ 145.2成交依据
拦截原因rvol=0.4 < 0.7被安检拦下的信号也要记——这是过滤器的绩效数据

被拦截的信号比成交的信号更有价值——它们告诉你过滤器拦对了还是拦错了（对照：后来行情证明该不该买）。

日志分级

  • INFO：信号、成交、日常轮询
  • WARN：风控拦截、余额异常、API 重试
  • ERROR：下单失败、API 断连、熔断触发
  • 日志按天滚动，保留 30 天——出问题能回溯

监控与通知

  • 成交通知：买入/卖出立即推送到手机（Telegram bot 或邮件）
  • 熔断通知：触发熔断必须人工确认才能恢复
  • API 连通性：每小时 ping 一次，断了发告警（IP 白名单失效就是这样被发现的）
  • 每日复盘报告：当日收益 vs 回测预期、实际滑点 vs 假设滑点、过滤器拦截率

二级结论： 监控的目标不是”少出事”，而是”出事时 10 分钟内知道、1 小时内能定位”。日志 + 通知 + 复盘三者闭环，实盘系统才算是活的。
